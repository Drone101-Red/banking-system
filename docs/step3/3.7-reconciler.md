# Paso 3.7 — Reconciliador de usuarios PENDING

## Objetivo

Implementar el reconciliador que recupera usuarios PENDING cuando
TigerBeetle vuelve a estar disponible.

**Contexto:** en Register (paso 3.5), si `CreateAccount` en TB falla
(por ejemplo, TB estaba caído), el usuario queda en PostgreSQL con
`status=PENDING`. Nadie lo recupera automáticamente. El reconciliador
cierra ese ciclo.

## Diseño

### Ciclo de vida

```text
main.go
  │
  ├── rootCtx, rootCancel := context.WithCancel(...)
  │
  ├── reconciler := recovery.NewReconciler(pg, tbClient)
  │
  ├── go reconciler.Start(rootCtx, interval)
  │
  └── en shutdown: rootCancel()
```

### Flujo de reconciliación

```text
ReconcileOnce(ctx):
  1. ListPendingUsers(ctx, 100)
  2. Si no hay PENDINGs -> return (0, 0, nil)
  3. Para cada usuario:
     a. AccountExists(tb_account_id) en TB
        - Existe      -> UpdateUserStatusActive
        - No existe   -> CreateAccount (idempotente) -> UpdateUserStatusActive
        - TB caído    -> dejar PENDING, contar como fallido
     b. Si UpdateUserStatusActive falla -> contar como fallido
  4. Log: "[recovery] ciclo: N OK, M fallidos"
```

### Start(ctx, interval)

```text
Start(ctx, interval):
  1. Ejecutar ReconcileOnce inmediatamente
  2. ticker := time.NewTicker(interval)
  3. for {
       select {
       case <-ctx.Done(): return
       case <-ticker.C:  ReconcileOnce
       }
     }
```

## Decisiones de diseño

### 1. PostgreSQL es la autoridad de identidad

El reconciliador **nunca** crea usuarios PostgreSQL a partir de cuentas
en TigerBeetle. Solo procesa usuarios que ya existen en PG con
`status=PENDING`.

Si TB tiene cuentas sin usuario PG asociado, es un problema de
observabilidad, no de reconciliación automática.

### 2. Caída de TB -> PENDING, no FAILED

Si TigerBeetle no está disponible, el usuario permanece PENDING. No se
introduce un estado FAILED porque:

- Los fallos de TB son típicamente temporales.
- Un estado FAILED requeriría una política de reintentos o intervención manual.
- PENDING ya representa "operación incompleta recuperable".

### 3. Idempotente

`ReconcileOnce` puede correrse N veces sin efectos secundarios:

- `CreateAccount` ya es idempotente (paso 2.4-bis.2).
- `UpdateUserStatusActive` usa `WHERE status='PENDING'`. Si el usuario
  ya está ACTIVE, afecta 0 filas y no falla.

### 4. Procesamiento en lotes

`BatchSize = 100` por ciclo. Si hay 10,000 PENDINGs:

- El reconciliador procesa 100 por ciclo.
- El siguiente ciclo (5 min después) procesa los siguientes 100.
- No bloquea el servidor HTTP.

### 5. Método independiente del ticker

`ReconcileOnce(ctx)` es público y ejecutable manualmente. Esto permite:

- Tests de integración sin esperar 5 minutos.
- Herramientas administrativas futuras.
- Debug manual.

`Start(ctx, interval)` es el wrapper con ticker que usa `main.go`.

### 6. Logs solo cuando hay trabajo

- Ciclo sin PENDINGs: no loggea.
- Ciclo con PENDINGs: loggea `procesando N usuarios` y `ciclo: N OK, M fallidos`.
- Errores individuales: siempre loggeados.

## Configuración

Variable de entorno:

```env
RECONCILE_INTERVAL_MINUTES=5
```

Default: 5 minutos. Configurable sin recompilar.

## Tests

### Integración (`reconciler_integration_test.go`)

Comando:

```bash
TB_TEST_ADDRESS=172.30.0.10:3000 \
POSTGRES_TEST_DSN="host=172.30.0.2 port=5432 user=banking_user password=secret123 dbname=banking sslmode=disable" \
go test -tags=integration -v ./internal/recovery
```

Tests:

1. **`PendingWithoutTB`** — crea PENDING, TB no tiene cuenta.
   Verifica que el reconciliador crea la cuenta y marca ACTIVE.

2. **`PendingWithTB`** — crea PENDING, TB ya tiene cuenta.
   Verifica que el reconciliador solo marca ACTIVE.

3. **`Idempotent`** — correr dos veces no rompe.
   La segunda ejecución no procesa al usuario ya ACTIVE.

4. **`EmptyQueue`** — no hay PENDINGs. No procesa nada.

## Cómo verificar

### 1. Levantar el stack

```bash
cd ~/proyectos/banking-system
docker compose up -d --build
sleep 30
```

### 2. Verificar que el reconciliador arrancó

```bash
docker logs banking-backend --tail 20 | grep -i recovery
```

Esperado:

```
[recovery] iniciando (intervalo: 5m0s)
```

### 3. Simular un PENDING manualmente

```bash
# Insertar un usuario PENDING sin cuenta TB
docker exec banking-postgres psql -U banking_user -d banking -c "
INSERT INTO users (email, password_hash, full_name, tb_account_id, status)
VALUES (
  'manual-' || extract(epoch from now())::bigint || '@test.local',
  '\$2a\$12\$dummy',
  'Manual Test',
  decode(repeat('ab', 16), 'hex'),
  'PENDING'
);
"
```

### 4. Esperar el siguiente ciclo (o forzar uno)

```bash
# Esperar hasta 5 minutos para el siguiente ciclo
sleep 300

# O alternativamente, reiniciar el backend para forzar la primera
# ejecución inmediata del reconciliador
docker compose restart backend
sleep 15
```

### 5. Verificar que se procesó

```bash
docker exec banking-postgres psql -U banking_user -d banking -c "
SELECT email, status FROM users WHERE email LIKE 'manual-%';
"
```

Esperado: `status = ACTIVE`.

## Deuda técnica documentada

| Deuda | Impacto | Trabajo futuro |
|---|---|---|
| Sin alertas si hay PENDINGs persistentes | Medio | Agregar métricas/alertas |
| Sin backoff si TB está caído mucho tiempo | Bajo | El ticker de 5 min ya limita reintentos |
| Sin límite de ciclos por usuario | Bajo | En producción, agregar contador de intentos |

## Notas para el futuro

**Regla:** los servicios de background (reconciliador, futuros workers)
deben usar `context.Context` para su ciclo de vida. `main.go` controla
el shutdown con un `rootCtx` cancelable.

**Regla:** los métodos que se ejecutan en background deben exponer una
versión "una sola vez" (`ReconcileOnce`) además del wrapper con ticker
(`Start`). Esto permite tests y ejecuciones manuales.
