# Bloque 3 — Autenticación: Cierre

## Resumen

El Bloque 3 implementa el sistema de autenticación completo:
registro, login, validación de tokens, reconciliación de usuarios
PENDING, y logout.

Al terminar el Bloque 3, el sistema puede:

1. Registrar usuarios con email + password + nombre.
2. Autenticar usuarios y emitir JWT.
3. Validar JWT en rutas protegidas.
4. Recuperar usuarios PENDING automáticamente.
5. Exponer logout (stateless, responsabilidad del cliente).

## Arquitectura final

### Endpoints

| Método | Ruta | Auth | Descripción |
|---|---|---|---|
| POST | /api/auth/register | No | Registrar usuario |
| POST | /api/auth/login | No | Login → JWT |
| POST | /api/auth/logout | No | Logout (stateless) |
| GET | /api/auth/me | Sí (Bearer) | Datos del usuario actual |

### Identidad dual

```text
PostgreSQL                    TigerBeetle
users.id (UUID)               account.id (uint128)
      │                              │
      └───── users.tb_account_id ────┘
```

- `users.id` = identidad de aplicación (JWT sub, relaciones).
- `tb_account_id` = identidad financiera (transferencias).
- El JWT lleva ambos en sus claims.

### Estados del usuario

```text
PENDING  →  ACTIVE
```

- **PENDING**: existe en PG, cuenta TB todavía no confirmada.
- **ACTIVE**: identidad completa, puede operar.
- **No hay FAILED**: las caídas de TB son temporales.

### Flujo de Register

```text
1. Validar + normalizar
2. Generar tb_account_id (crypto/rand)
3. Hash password (bcrypt cost 12)
4. INSERT users status=PENDING
5. CreateAccount en TB
6. UPDATE users status=ACTIVE
7. Devolver 201 con user
```

Si el paso 5 falla → usuario queda PENDING.
El reconciliador lo recupera en el siguiente ciclo.

### Flujo de Login

```text
1. Normalizar email
2. Validar email/password no vacíos
3. Buscar usuario:
   - No existe → dummy bcrypt + 401 INVALID_CREDENTIALS
4. Comparar password:
   - No coincide → 401 INVALID_CREDENTIALS
5. Verificar status:
   - PENDING → 401 ACCOUNT_PENDING
   - ACTIVE → continuar
6. Generar JWT
7. Devolver 200 con token + user
```

### Reconciliador

```text
Start(ctx, interval):
  1. ReconcileOnce inmediato
  2. ticker cada interval
  3. Cada ciclo: procesa hasta 100 PENDINGs
     - AccountExists → UpdateUserStatusActive
     - !AccountExists → CreateAccount → UpdateUserStatusActive
```

**Configuración:** `RECONCILE_INTERVAL_MINUTES=5` (default).

## Seguridad implementada

| Aspecto | Implementación |
|---|---|
| Password storage | bcrypt cost 12 |
| Password limits | 8-72 bytes, sin truncar |
| JWT algorithm | HS256, rechaza `alg: none` |
| JWT issuer | `banking-system`, rechaza otros |
| JWT expiry | 24 horas |
| Anti-enumeración | Mismo error para email inexistente y password incorrecta |
| Timing attack | Dummy bcrypt pre-generado |
| Middleware | Valida forma de claims antes de inyectarlos |
| DisallowUnknownFields | Rechaza JSON con campos inesperados |

## Hallazgos documentados

### 1. `golang.org/x/crypto v0.57.0` requiere Go 1.26

Al instalar la dependencia para bcrypt, la versión más reciente subió
el `go directive` del `go.mod` a 1.26.0, rompiendo el Dockerfile con
`golang:1.24-bookworm`.

**Solución:** fijar a `v0.47.0` (compatible con Go 1.24).

### 2. `JWT_SECRET` con caracteres especiales rompe Docker Compose

El secreto base64 con `+`, `/`, `=` causó:

```text
invalid interpolation format for services.backend.environment.JWT_SECRET.
```

**Solución:** regenerar en hex con `openssl rand -hex 32`.

### 3. Docker Compose no hereda el `.env`

Cada variable crítica debe declararse explícitamente en
`environment:` del servicio que la necesita.

### 4. Dependencias no usadas desaparecen del `go.mod`

El orden correcto es:
1. Escribir código que importe la dependencia.
2. `go get` o `go mod tidy`.

## Reglas del proyecto consolidadas

1. **Después de `go get` o `go mod tidy`:** verificar que `go.mod`
   siga diciendo `go 1.24.0`.
2. **Los secretos para Docker Compose:** usar hex o base64url sin
   padding. Evitar base64 estándar.
3. **Cada variable crítica del `.env`:** declararla explícitamente en
   `environment:` del compose.
4. **Los secretos sensibles:** nunca commitear al repo (`.env` en
   `.gitignore`).
5. **Los servicios de background:** usar `context.Context` para su
   ciclo de vida.
