# Paso 3.5 — Implementación de Register

## Objetivo

Implementar `POST /api/auth/register` con el flujo PENDING → ACTIVE
definido en `docs/step3/3.1-3.4-auth-design.md`.

Al terminar 3.5, un cliente puede:

1. Enviar `{email, password, full_name}` a `POST /api/auth/register`.
2. Recibir `201 Created` con `{id, email, full_name, status: "ACTIVE"}`.
3. El usuario queda persistido en PostgreSQL con la contraseña hasheada.
4. La cuenta financiera queda creada en TigerBeetle.

## Componentes

### 1. `password/password.go`

Encapsula el hashing y comparación de contraseñas.

- `Hash(plain) (string, error)` — bcrypt cost 12, valida longitud 8..72 bytes.
- `Compare(hash, plain) error` — verifica coincidencia.
- **No trunca passwords silenciosamente.** Si tiene >72 bytes, error.

### 2. `auth/service.go`

Orquesta el flujo de registro:

```text
Register(ctx, req):
  1. Normalizar email (lowercase + trim) y full_name (trim).
  2. Validar campos.
  3. Generar tb_account_id (crypto/rand 16 bytes, rechaza 0 y 1).
  4. Hash password (bcrypt cost 12).
  5. INSERT users con status=PENDING.
  6. CreateAccount en TigerBeetle.
  7. UPDATE status=ACTIVE.
  8. Devolver user con status=ACTIVE.
```

**Si el paso 6 falla:** el usuario queda PENDING. El reconciliador
(implementado en 3.7+) lo recuperará en el siguiente ciclo.

**Si el paso 7 falla:** mismo razonamiento. El usuario quedará PENDING
y se recuperará después.

**Interfaz `TBAccountCreator`:** permite mockear TB en tests unitarios.

### 3. `auth/handler.go`

- `RegisterHandler` — POST /api/auth/register.
- `DisallowUnknownFields` — rechaza campos no esperados.
- Respuesta 201 con `{id, email, full_name, status}`.
- `PasswordHash` y `TBAccountID` con `json:"-"` — no se filtran.

### 4. `main.go`

- Wiring: `authService := auth.NewService(pg, tbClient)`.
- Ruta: `r.Post("/api/auth/register", authHandler.RegisterHandler)`.

## Tests

### Unitarios (sin dependencias externas)

**`password/password_test.go` (7 tests):**

- Hash válido → string bcrypt cost 12.
- Hash con plain <8 bytes → ErrTooShort.
- Hash con plain >72 bytes → ErrTooLong.
- Hash con plain exactamente 72 bytes → OK.
- Compare con password correcta → nil.
- Compare con password incorrecta → ErrMismatch.
- Dos hashes del mismo plain difieren pero ambos válidos.

**`auth/service_test.go` (8 tests):**

- `validateRegister`: valid, empty email, invalid email, empty name,
  short password, long password.
- `generateTBAccountID`: válido, aleatoriedad (100 sin colisión).

### Integración (contra Postgres + TB reales, build tag `integration`)

**`auth/register_integration_test.go` (7 tests):**

- `HappyPath` — registro completo, devuelve user con status=ACTIVE.
- `DuplicateEmail` — rechaza con EMAIL_EXISTS.
- `InvalidEmail` — rechaza antes de tocar DB.
- `ShortPassword` — rechaza antes de tocar DB.
- `EmailNormalization` — uppercase + espacios se normalizan.
- `PersistsToPostgres` — el usuario queda persistido con bcrypt.

## Hallazgo: `golang.org/x/crypto v0.57.0` requiere Go 1.26

Al instalar `golang.org/x/crypto` para bcrypt, la versión más reciente
(`v0.57.0`) requiere Go >= 1.26. Al ejecutar `go mod tidy`, **sube
automáticamente el `go directive` del `go.mod` a `1.26.0`**,
rompiendo el build en Docker (`golang:1.24-bookworm`).

**Solución:** fijar `golang.org/x/crypto` a `v0.47.0`, que es compatible
con Go 1.24.

```bash
go get golang.org/x/crypto@v0.47.0
go mod edit -go=1.24
go mod tidy
```

**Documentado como deuda:** futuras actualizaciones de `x/crypto` deben
verificar compatibilidad con Go 1.24.

## Casos de error cubiertos

| Caso | HTTP | Código |
|---|---|---|
| JSON inválido | 400 | `INVALID_REQUEST` |
| Email vacío | 400 | `EMAIL_REQUIRED` |
| Email inválido | 400 | `EMAIL_INVALID` |
| Email > 255 chars | 400 | `EMAIL_TOO_LONG` |
| full_name vacío | 400 | `FULL_NAME_REQUIRED` |
| Password < 8 bytes | 400 | `PASSWORD_TOO_SHORT` |
| Password > 72 bytes | 400 | `PASSWORD_TOO_LONG` |
| Email duplicado | 409 | `EMAIL_EXISTS` |
| Colisión de tb_account_id | 409 | `TB_ACCOUNT_ID_COLLISION` |
| TigerBeetle caído | 500 | `INTERNAL_ERROR` |
