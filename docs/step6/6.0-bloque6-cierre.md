# Bloque 6 — Frontend React: Cierre

## Resumen

El Bloque 6 implementa la interfaz web del sistema: una SPA en React 19
con Vite 8 y Tailwind 3.4. Consume los 15 endpoints del backend mediante
axios con interceptores JWT. Se sirve desde nginx en Docker.

Al terminar el Bloque 6, el sistema completo se levanta con
`docker compose up` y es accesible desde el navegador.

## Decisiones arquitectónicas

### 1. Doble capa de estado

- **AuthContext (global):** `user`, `tbAccountID`, `loading`. Datos que
  no cambian durante la sesión.
- **useBalance() (local por página):** `balance`, `refresh()`. Datos
  que cambian después de cada operación.

**Razón:** separar estado persistente de estado operativo. Cada página
decide cuándo consultar el saldo.

### 2. `tb_account_id` desde el JWT

El `tb_account_id` **no viene de `/api/auth/me`**. Viene del payload
del JWT (decode en el cliente).

**Razón:** `/api/auth/me` devuelve identidad (email, nombre, alias). El
JWT ya contiene el `tb_account_id`. Evita un fetch extra.

**Importante:** el decode **no verifica la firma**. Solo se usa para
leer `tb_account_id` como dato auxiliar. Nunca para autorizar operaciones.

### 3. Balance centralizado con `useBalance()`

Antes: cada componente llamaba a `/api/account/balance` por su cuenta.

Ahora: un hook centraliza. Después de cualquier operación exitosa se
llama a `refresh()`.

**Ejemplo en el Chat:**

```jsx
<Chat onBalanceChange={refreshBalance} />
```

Cuando el usuario confirma una operación en el chat, el saldo se
actualiza automáticamente en el Dashboard.

### 4. Carga secuencial en el Dashboard

**Problema:** el Dashboard carga saldo + últimas 5 transacciones en
paralelo. Bajo carga, TigerBeetle encola las operaciones y puede
superar el timeout de 5s.

**Solución:** cargar en serie.

```jsx
useEffect(() => {
  async function load() {
    await refreshBalance();
    const { data } = await api.get('/api/transactions/history', {...});
    setRecentTxs(data.transactions);
  }
  load();
}, []);
```

**Resultado:** sin timeouts, sin 500.

### 5. Confirmación en el chat (dos fases)

**El chat es la pieza más compleja** porque maneja operaciones
financieras en dos fases.

```
1. Usuario escribe "Deposita $50"
2. POST /api/chat
3. Backend responde con pending_confirmation
4. Chat guarda pendingConfirmation en estado
5. Se muestra banner amarillo con [Confirmar] [Cancelar]
6. Si confirma: POST /api/chat/confirm con el token
7. Backend ejecuta
8. Se refresca el saldo vía onBalanceChange()
```

**Puntos clave:**

| Aspecto | Implementación |
|---|---|
| Input del usuario | Deshabilitado mientras hay `pendingConfirm` |
| Botón "Confirmar" | Llama a `confirmOperation()`, no a `sendMessage()` |
| Botón "Cancelar" | Limpia `pendingConfirm` sin llamar al backend |
| Refresco de saldo | `onBalanceChange` callback del padre |

### 6. Logout stateless

**El backend expone `POST /api/auth/logout` pero no mantiene blacklist.**
El cierre de sesión es responsabilidad del cliente:

```js
function logout() {
  localStorage.removeItem('token');
  setUser(null);
  setTbAccountID(null);
}
```

**No se llama al endpoint.** El token sigue válido hasta expirar, pero
el cliente lo olvida.

### 7. `user` NO se persiste en localStorage

**Solo el token se guarda.** El `user` se restaura siempre vía
`/api/auth/me` al montar el `AuthProvider`.

**Razón:** evita que información vieja del usuario se convierta
accidentalmente en fuente de verdad.

## Patrones

### Montos

Siempre en centavos en el backend. Conversión en el frontend:

```js
const display = `$${(cents / 100).toFixed(2)}`;
const inputToCents = (usd) => Math.round(parseFloat(usd) * 100);
```

**Nunca usar `float64` para manipular dinero.**

### Idempotencia

Las operaciones de escritura (deposit, withdraw, transfer) envían un
header `Idempotency-Key` generado con `crypto.randomUUID()`.

```js
const idempotencyKey = crypto.randomUUID();
await api.post(endpoint, body, {
  headers: { 'Idempotency-Key': idempotencyKey },
});
```

### Fechas

Todos los timestamps vienen en ISO 8601 UTC. Formateo local:

```js
new Date(iso).toLocaleString('es-ES', {
  day: '2-digit',
  month: 'short',
  year: 'numeric',
  hour: '2-digit',
  minute: '2-digit',
});
// → "15 sep 2026, 18:35"
```

### Errores

Mostrar `message` del backend, no `code`. Excepción: algunos códigos
se mapean a mensajes más claros.

```js
if (code === 'INSUFFICIENT_FUNDS') setError('Saldo insuficiente para esta operación');
else if (code === 'SAME_ACCOUNT') setError('No puedes transferir a tu propia cuenta');
else setError(message);
```

## Docker

### Dockerfile

Multi-stage:

- **Builder:** `node:20-alpine` + `npm ci` + `npm run build`.
- **Runtime:** `nginx:alpine` + solo `dist/` y `nginx.conf`.
- **Tamaño final:** ~30-40 MB.

### nginx.conf

- **SPA fallback:** `try_files $uri $uri/ /index.html`.
- **Proxy `/api`:** `proxy_pass http://backend:8080/api/`.
- **Timeout 120s:** el chat con LLM puede tardar.
- **Gzip:** reduce tamaño de transferencia.
- **Cache de assets:** 1 año para `/assets/` (nombres con hash).

### docker-compose.yml

```yaml
frontend:
  build:
    context: ./frontend
    dockerfile: Dockerfile
  container_name: banking-frontend
  depends_on:
    - backend
  ports:
    - "80:80"
  networks:
    - banking_net
```

## Problemas encontrados y solución

### Timeout de TigerBeetle

**Síntoma:** el endpoint `/api/account/balance` devolvía 500 esporádicamente
con `get balance timeout after 2s`.

**Causa:** el Dashboard lanzaba 2 requests concurrentes (saldo + historial).
La tercera operación superaba el timeout de 2s por la cola interna de TB.

**Fix:**
1. Subir `accountLookupTimeout` de 2s a 5s en el backend.
2. Serializar las requests del Dashboard en el frontend.

### Nombre de archivo case-sensitive

**Síntoma:** `git add frontend/Dockerfile` fallaba con "did not match".

**Causa:** el archivo se llamaba `dockerfile` (minúscula). Docker lo
acepta en Linux, pero Git es case-sensitive.

**Fix:** renombrar a `Dockerfile` (con D mayúscula).
