# Bloque 4 — Transacciones: Cierre

## Resumen

El Bloque 4 implementa las operaciones financieras del sistema:
depósito, retiro, transferencia entre usuarios, e historial paginado.
Además, expone los endpoints de consulta de cuenta (info y saldo).

Todas las operaciones se ejecutan contra TigerBeetle, que es la fuente
de verdad financiera. PostgreSQL mantiene un índice de lectura
(`transactions_log`) para responder el historial rápido.

## Endpoints implementados

| Método | Ruta | Auth | Descripción |
|---|---|---|---|
| POST | `/api/transactions/deposit` | JWT | Depositar fondos |
| POST | `/api/transactions/withdraw` | JWT | Retirar fondos |
| POST | `/api/transactions/transfer` | JWT | Transferir a otra cuenta |
| GET | `/api/transactions/history` | JWT | Historial paginado |
| GET | `/api/account` | JWT | Info de la cuenta |
| GET | `/api/account/balance` | JWT | Saldo en centavos |

## Arquitectura

### Flujo de una transferencia

```text
POST /api/transactions/deposit
       │
       ▼
Handler (delgado, solo HTTP)
       │
       ▼
Service (lógica de negocio)
       │
       ├── Validar monto > 0
       ├── Buscar usuario (getActiveUser)
       ├── Construir Transaction
       │
       ▼
TigerBeetle.CreateTransfer
       │
       ├── TransferCreated  → OK
       ├── TransferExists   → OK (idempotente)
       ├── TransferExceedsCredits → 400 INSUFFICIENT_FUNDS
       └── otro → error
       │
       ▼
PostgreSQL.InsertTransactionLog
       │
       └── Si falla: loggear (no revertir TB)
       │
       ▼
Respuesta 201 con Transaction
```

### Doble entrada

Cada operación es una transferencia entre dos cuentas:

| Operación | Debit | Credit | Code |
|---|---|---|---|
| Deposit | Banco (ID=1) | Usuario | 1 |
| Withdraw | Usuario | Banco (ID=1) | 2 |
| Transfer | Usuario origen | Usuario destino | 3 |

TigerBeetle garantiza la consistencia: el dinero nunca se crea ni se
destruye, solo se mueve entre cuentas.

## Reglas del Bloque 4

1. **TigerBeetle es la fuente de verdad financiera.** El saldo se calcula
   como `credits_posted - debits_posted` en TB.
2. **PostgreSQL mantiene un índice de lectura** (`transactions_log`) para
   responder el historial rápido.
3. **Dinero siempre en centavos (`int64`).** Nunca `float64`.
4. **Si TB rechaza, error.** Si TB acepta pero el log falla, se loggea
   y se devuelve éxito (la transferencia SÍ se hizo).
5. **Validar destino:** existe en PG, está ACTIVE, y es distinto del origen.
6. **Idempotencia:** `CreateTransfer` con el mismo ID devuelve
   `TransferExists` que se trata como OK.

## Hallazgos del Bloque 4

### 1. Endianness de `Uint128.Bytes()`

Los tests de integración fallaron con `balance = 0` porque
`uint128ToInt64` asumía big-endian y leía los bytes 8..15.

TigerBeetle serializa Uint128 en **little-endian** (byte 0 = LSB).
Verificado empíricamente:

```text
tb.ToUint128(12000).Bytes() = e02e0000...
```

**Fix:** usar `encoding/binary.LittleEndian.Uint64(b[:8])`.

**Lección:** no asumir endianness. Verificar empíricamente antes de
implementar conversiones de bytes a números.

### 2. Respuesta incompleta en deposit/withdraw/transfer

Los handlers devolvían `Transaction` con `id`, `created_at`,
`debit_account_id` y `credit_account_id` vacíos, porque
`InsertTransactionLog` no usaba `RETURNING`.

**Fix:** `INSERT ... RETURNING id, created_at` + `tx.FillHex()`.

### 3. Rutas de account mal ubicadas

Al integrar `/api/account`, las rutas quedaron dentro del
`Route("/api/transactions")`, registrando `/api/transactions/` y
`/api/transactions/balance`.

**Fix:** usar `r.Group` con paths completos.

## Deuda técnica documentada

| Deuda | Impacto | Trabajo futuro |
|---|---|---|
| `transactions_log` puede desincronizarse de TB | Medio | Job de reconciliación |
| `generateTransferID` usa timestamp (no crypto/rand) | Bajo | crypto/rand con idempotencia por hash |
| Sin límite diario por usuario | Medio | Fuera de scope |
| Tests crean usuarios sin cleanup | Bajo | Usar DB separada o DELETE al final |

## Cómo verificar

### 1. Levantar el stack

```bash
cd ~/proyectos/banking-system
docker compose up -d --build
sleep 30
```

### 2. Registrar y login

```bash
curl -s -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"juan@example.com","password":"TestPassword123!","full_name":"Juan Pérez"}'

TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"juan@example.com","password":"TestPassword123!"}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])")
```

```bash
curl -s -X POST http://localhost:8080/api/transactions/deposit \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"amount_cents": 10000}' \
  | python3 -m json.tool
```

```bash
  -H "Authorization: Bearer $TOKEN" \
```
