# Paso 2.4 — Retry de conexión con TigerBeetle

## Objetivo

Evitar que el backend falle inmediatamente si TigerBeetle todavía no está
disponible durante el arranque de los contenedores.

## Política

El backend utiliza el siguiente mecanismo:

- 5 intentos máximos.
- Primer intento inmediato.
- 2 segundos entre intentos fallidos.
- No se espera después del último intento.
- Si un intento tiene éxito, el proceso termina inmediatamente.
- Si `tb.NewClient()` crea un cliente pero `Ping()` falla, el cliente se cierra
  antes del siguiente intento.
- Después de agotar los intentos, se devuelve el último error.

Tiempo máximo aproximado de espera:

```text
4 × 2 segundos = 8 segundos

El primer intento no añade espera.

Diseño

El retry se implementa como lógica Go pura mediante una función que recibe:

cantidad máxima de intentos;
intervalo entre intentos;
operación a ejecutar.

Esto permite probar el comportamiento sin depender de Docker ni de un
TigerBeetle real.

Tests

Se verifican dos escenarios:

La operación falla dos veces y tiene éxito en el tercer intento.
La operación falla en los cinco intentos y devuelve el error.
Integración

New() utiliza el retry para:

crear el cliente TigerBeetle;
ejecutar Ping() mediante Nop();
cerrar el cliente si el ping falla;
devolver el cliente solamente cuando la conexión fue verificada.
Verificación

Tests unitarios:

go test ./internal/tigerbeetle

Resultado:

ok  	banking-system/internal/tigerbeetle

Suite completa:

go test ./...

Resultado:

ok  	banking-system/internal/tigerbeetle

Integración:

curl -i http://localhost:8080/health

Resultado:

HTTP/1.1 200 OK

con PostgreSQL y TigerBeetle reportando ok.

Decisión

Se utiliza un retry simple y acotado en lugar de reintentos infinitos.
Esto permite tolerar el orden de arranque de Docker sin ocultar un fallo
permanente de TigerBeetle.
