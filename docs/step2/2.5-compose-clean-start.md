# Paso 2.5 — Compose completo y arranque limpio

## Objetivo

Verificar que PostgreSQL, TigerBeetle y el backend puedan destruirse y recrearse completamente desde cero sin depender de recursos anteriores ni de IPs dinámicas.

## Problema encontrado

Inicialmente `TB_ADDRESS` utilizaba una IP dinámica:

`172.18.0.2:3000`

Después de ejecutar:

`docker compose down -v`

Docker recreó la red y TigerBeetle recibió otra IP:

`172.18.0.3`

El backend continuó intentando conectarse a la IP anterior y `/health` falló con:

`curl: (56) Recv failure: Connection reset by peer`

## Solución

Se configuró una red Docker explícita:

- Subnet: `172.30.0.0/24`
- TigerBeetle: `172.30.0.10`
- PostgreSQL y backend conectados a la misma red.

TigerBeetle utiliza:

`TB_ADDRESS=172.30.0.10:3000`

La IP de TigerBeetle queda definida explícitamente mediante `ipv4_address`, evitando depender de asignación dinámica.

## Verificación

Se ejecutó:

`docker compose down -v`

seguido de:

`docker compose up -d --build`

Resultado:

- `banking-postgres` → Up (healthy)
- `banking-tigerbeetle` → Up (healthy)
- `banking-backend` → Up
- TigerBeetle → `172.30.0.10`

Health check:

`HTTP/1.1 200 OK`

Respuesta:

`{"postgres":"ok","status":"healthy","tigerbeetle":"ok"}`

## Lección

Una IP interna dinámica de Docker no debe utilizarse como configuración permanente de conexión entre servicios cuando el cliente requiere una dirección IP en lugar de un hostname.

La configuración de red explícita permite que el backend encuentre TigerBeetle después de una recreación completa del entorno.
