# Paso 2.2 — TigerBeetle con entrypoint idempotente

## Objetivo
Levantar TigerBeetle en Docker con un entrypoint que formatea el datafile
solo la primera vez, y verificar que arranca, acepta conexiones en el
puerto 3000, y es idempotente al reiniciar.

## Archivos involucrados
- `docker-compose.yml` (agrega el servicio `tigerbeetle` y el volumen `tb_data`)
- `scripts/tb-entrypoint.sh` (nuevo, idempotente)

## Por qué un entrypoint custom

TigerBeetle **no arranca directamente** desde la imagen oficial. Requiere:

1. `tigerbeetle format` — crea el datafile. Solo debe correr una vez.
2. `tigerbeetle start` — arranca el servidor apuntando al datafile.

El entrypoint hace el format condicional (si el archivo no existe) y luego
el start. Es idempotente: reiniciar el contenedor no borra datos.

## Flags críticos de 0.17.9

- `--development`: **obligatorio** en single-replica. Sin este flag, TB
  espera un quórum de 6 réplicas y se queda colgado.
- `--cluster=0`, `--replica=0`, `--replica-count=1`: identifican el clúster.
  Cluster ID = 0 como constante compartida con el cliente Go.
- El datafile va como **argumento posicional al final**, no con flag.
- `--addresses=0.0.0.0:3000`: 0.0.0.0 para que sea accesible desde otros
  contenedores de la red de compose.

## `security_opt: seccomp=unconfined`

Docker 25+ bloquea `io_uring` por defecto con su perfil seccomp. TigerBeetle
usa `io_uring` intensivamente para I/O. Sin este flag, TB falla al arrancar
con errores crípticos de "operation not permitted".

## Cómo levantar

```bash
docker compose up -d tigerbeetle
Primera vez descarga la imagen (~30-40 MB).

Cómo verificar
1. El contenedor está corriendo y healthy
bash
docker ps --filter name=banking-tigerbeetle
# Esperado: STATUS "Up X seconds (healthy)"
2. El entrypoint formateó el datafile la primera vez
bash
docker logs banking-tigerbeetle --tail 30
Esperado (primera corrida):

text
[tb-entrypoint] Datafile no existe. Formateando...
[tb-entrypoint] Formateo completado.
[tb-entrypoint] Iniciando TigerBeetle en 0.0.0.0:3000...
Esperado (segunda corrida con volumen persistente):

text
[tb-entrypoint] Datafile ya existe. Saltando format.
[tb-entrypoint] Iniciando TigerBeetle en 0.0.0.0:3000...
3. TB está escuchando
bash
docker logs banking-tigerbeetle | grep -i "listening\|started\|address"
Esperado: línea con 0.0.0.0:3000 o similar.

4. El puerto responde
bash
nc -zv localhost 3000
# Esperado: "Connection to localhost 3000 port [tcp/*] succeeded!"
Si nc no está instalado en el host:

bash
docker exec banking-tigerbeetle nc -z localhost 3000 && echo "OK"
5. El datafile existe dentro del volumen
bash
docker exec banking-tigerbeetle ls -la /data/
# Esperado: archivo 0_0.tigerbeetle con tamaño > 0
6. Idempotencia: reiniciar no reformatea
bash
docker compose restart tigerbeetle
sleep 5
docker logs banking-tigerbeetle --tail 5
# Esperado: "[tb-entrypoint] Datafile ya existe. Saltando format."
Troubleshooting
El contenedor reinicia en loop con "operation not permitted"
Falta security_opt: seccomp=unconfined. Confírmalo en docker-compose.yml.

El contenedor queda en "starting" y nunca pasa a healthy
Posibles causas:

--development faltante en el entrypoint → TB espera quórum.

--addresses con formato incorrecto.

Datafile corrupto de una corrida previa.

Diagnóstico:

bash
docker logs banking-tigerbeetle --tail 50
Si el datafile está corrupto o quieres empezar de cero:

bash
docker compose down -v    # borra el volumen tb_data
docker compose up -d tigerbeetle
nc -z falla pero el contenedor parece vivo
Es normal los primeros 2-3 segundos. El healthcheck tiene retries: 10
con interval: 5s, así que hay 50 segundos de margen. Si después de eso
sigue unhealthy, hay un problema real.

Nota: nc -z solo verifica que el puerto esté abierto, no que TB esté
listo para aceptar conexiones del cliente Go. Es suficiente para este paso,
pero el backend (paso 2.4) implementará un retry loop al conectar. Ver
tigerbeetle.go para el detalle.

bash
