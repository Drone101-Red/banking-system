# Confirmación de operaciones en el backend

## Problema

El chat con IA permite al usuario ejecutar operaciones financieras
en lenguaje natural. Pero confiar en el modelo para pedir confirmación
es riesgoso:

- El modelo puede ignorar el system prompt.
- Un jailbreak puede saltarse la confirmación.
- OpenRouter puede cambiar el modelo por detrás.
- Un prompt ambiguo produce comportamientos inesperados.

**El backend no debe confiar en el modelo para decisiones críticas.**

## Solución: two-phase commit

El backend implementa un flujo de **dos fases** para operaciones de
escritura (`deposit`, `withdraw`, `transfer`).

### Fase 1: el modelo propone

```text
Usuario: "Deposita $25"
   │
   ▼
Modelo: tool_call deposit(amount_cents=2500)
   │
   ▼
Backend: NO ejecuta.
         Crea PendingOperation en PostgreSQL.
         Devuelve token al cliente.
   │
   ▼
Cliente: {reply: "¿Confirmas?", pending_confirmation: {token: "abc..."}}
```

**El modelo NUNCA ejecuta la operación directamente.** Solo la propone.

### Fase 2: el usuario confirma

```text
Usuario: "Sí, confirmo"
   │
   ▼
Cliente: POST /api/chat/confirm {confirmation_token: "abc..."}
   │
   ▼
Backend: valida token (existe, no usado, no expirado, del usuario)
         ejecuta la operación
   │
   ▼
Cliente: {success: true, message: "Depósito ejecutado"}
```

## Endpoints

### `POST /api/chat`

**Request:**

```json
{
  "message": "Deposita $25",
  "history": [...]
}
```

**Response 200 (con pending):**

```json
{
  "reply": "Voy a depositar $25.00. ¿Confirmas?",
  "tool_calls": [
    {
      "id": "call_abc",
      "type": "function",
      "function": {"name": "deposit", "arguments": "{\"amount_cents\": 2500}"}
    }
  ],
  "pending_confirmation": {
    "confirmation_token": "4804d83e-a526-4c8c-b53e-0faa1a12252e",
    "type": "deposit",
    "amount_cents": 2500,
    "expires_at": "2026-09-15T18:10:40Z"
  },
  "usage": {...}
}
```

**El campo `pending_confirmation` es la clave.** Contiene el token que
el cliente debe presentar para ejecutar.

### `POST /api/chat/confirm`

**Request:**

```json
{
  "confirmation_token": "4804d83e-a526-4c8c-b53e-0faa1a12252e"
}
```

**Response 200:**

```json
{
  "success": true,
  "message": "Operación 'deposit' ejecutada correctamente",
  "operation": "deposit"
}
```

**Errores:**

| Código | Situación |
|---|---|
| `CONFIRMATION_NOT_FOUND` | Token inválido, expirado, ya usado, o de otro usuario |
| `MISSING_TOKEN` | Body sin `confirmation_token` |
| `TOKEN_REQUIRED` | Sin JWT |

## Schema

```sql
CREATE TABLE pending_confirmations (
    token         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    operation     JSONB NOT NULL,
    expires_at    TIMESTAMP NOT NULL,
    used_at       TIMESTAMP,
    created_at    TIMESTAMP DEFAULT NOW()
);
```

**Campos clave:**

- `token`: UUID generado por PostgreSQL.
- `user_id`: FK a users. Ata el token a un usuario.
- `operation`: JSONB con `{type, amount_cents, to_account_id}`.
- `expires_at`: **`NOW() + 5 minutos` en UTC**.
- `used_at`: NULL si está pendiente, timestamp si se ejecutó.

## Garantías

| Garantía | Cómo |
|---|---|
| **Un solo uso** | `UPDATE ... SET used_at = NOW() WHERE used_at IS NULL` |
| **Expiración** | `WHERE expires_at > NOW()` |
| **Dueño correcto** | `WHERE user_id = $2` |
| **Atómico** | El UPDATE+RETURNING es una sola operación |
| **Sin reuso** | Una vez que `used_at` está seteado, `Consume` falla |
| **Sin spoofing** | El `userID` viene del JWT, no del body |

## Flujo con concurrencia

Si dos requests intentan confirmar el mismo token simultáneamente:

```text
Request A: UPDATE ... WHERE used_at IS NULL RETURNING operation
Request B: UPDATE ... WHERE used_at IS NULL RETURNING operation

Resultado: solo una matchea (la primera que llega).
La otra recibe 0 filas → CONFIRMATION_NOT_FOUND.
```

**PostgreSQL garantiza atomicidad.** No hay race condition.

## System prompt

El system prompt es **explícito** sobre el flujo:

```text
OPERACIONES DE ESCRITURA (deposit, withdraw, transfer):
Cuando el usuario pida una operación de escritura, LLAMA A LA TOOL
INMEDIATAMENTE, sin pedir confirmación previa.

La tool NO ejecutará la operación. Devolverá un resultado con
status="pending_confirmation" y un token. En ese momento:
  1. Informa al usuario qué operación está pendiente.
  2. Pide confirmación explícita ("¿Confirmas?").
  3. El frontend llamará a POST /api/chat/confirm con el token.
  4. Tú NO necesitas llamar a ninguna tool adicional.

NUNCA pidas confirmación ANTES de llamar a la tool.
```

**La frase "LLAMA A LA TOOL INMEDIATAMENTE" es crítica.**
Sin ella, el modelo pedía confirmación **antes** de llamar a la tool,
y el backend nunca creaba el token.

## Hallazgo: timezone

**Bug encontrado en los tests de integración:**

Los tests fallaban con `CONFIRMATION_NOT_FOUND` porque el token
parecía expirado inmediatamente.

**Causa:**

- PostgreSQL usa **UTC** para `NOW()` en columnas `TIMESTAMP`.
- Go usa **hora local** para `time.Now()`.
- Si la VM está en UTC-5, `expires_at` (15:31 local) queda **antes**
  que `NOW()` (20:31 UTC). El token parece expirado.

**Fix:**

```go
time.Now().UTC().Add(ConfirmationTTL)
```

**Lección:** siempre usar `time.Now().UTC()` para timestamps que se
persisten en PostgreSQL.

**Trabajo futuro:** migrar las columnas a `TIMESTAMPTZ` (con timezone)
para que PostgreSQL normalice automáticamente.

## Flujo completo (ejemplo real)

```bash
# 1. Usuario pide depósito
RESP1=$(curl -s -X POST http://localhost:8080/api/chat \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"message":"Deposita $25 a mi cuenta"}')

# RESP1:
# {
#   "reply": "Voy a depositar $25.00. ¿Confirmas?",
#   "pending_confirmation": {
#     "confirmation_token": "4804d83e-a526-4c8c-b53e-0faa1a12252e",
#     "type": "deposit",
#     "amount_cents": 2500
#   }
# }

# 2. Extraer el token
TOKEN_CONFIRM=$(echo "$RESP1" | jq -r '.pending_confirmation.confirmation_token')

# 3. Confirmar
curl -X POST http://localhost:8080/api/chat/confirm \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"confirmation_token\":\"$TOKEN_CONFIRM\"}"

# Response:
# {
#   "success": true,
#   "message": "Operación 'deposit' ejecutada correctamente",
#   "operation": "deposit"
# }

# 4. Verificar saldo
curl -X GET http://localhost:8080/api/account/balance \
  -H "Authorization: Bearer $TOKEN"
# {"balance_cents": 6500}
```

## Deuda técnica

| Deuda | Impacto | Trabajo futuro |
|---|---|---|
| Columnas `TIMESTAMP` sin timezone | Medio | Migrar a `TIMESTAMPTZ` |
| Sin cleanup automático de tokens expirados | Bajo | Job periódico o `pg_cron` |
| Sin notificación al usuario cuando expira | Bajo | Frontend puede hacer polling |
